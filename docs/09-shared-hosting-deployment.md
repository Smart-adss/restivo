# 09 — النشر على الاستضافة المشتركة

**المشروع:** Restaurant SaaS Platform  
**التاريخ:** 17 نوفمبر 2026  
**حالة القدرات الإنتاجية:** غير معروفة. هذه الوثيقة تصف طريقة النشر وأسئلة التحقق. لا تفترض أن Cron أو CLI أو Composer موجودون على المزوّد حتى تُجاب أسئلة [15-decisions-and-assumptions.md](15-decisions-and-assumptions.md).

## 1. تصنيف المكونات

| المكوّن | التصنيف | ملاحظة النشر |
|---|---|---|
| تطبيق PHP Laravel | 1 | إذا تحققت امتدادات PHP |
| Blade + Livewire + Alpine | 1 | تُرفع ملفات PHP وJS مجمعة |
| Tailwind / Vite | 2 | البناء على جهاز التطوير |
| MySQL InnoDB | 1 | شرط DDL |
| جلسات قاعدة البيانات | 1 | جدول `sessions` |
| كاش ملفات | 1 | مجلد `storage/framework/cache` قابل للكتابة |
| طابور قاعدة البيانات | 2 | Cron |
| مجدول | 2 | Cron كل دقيقة |
| استطلاع قصير | 1 | من المتصفح |
| استطلاع طويل | 4 | لا يُستخدم |
| WebSocket ذاتي | 4 | لا يُستخدم |
| Redis / Supervisor / Docker / Node إنتاجي | 4 | لا يُستخدم |
| SMTP خارجي أو SMTP الاستضافة | 3 أو 2 | خدمة أو ميزة مزوّد بعد اختبار |
| بوابة دفع | 3 | حساب تاجر واتصال HTTPS صادر |
| تخزين كائنات | 3 | فقط عند ضيق القرص |
| نسخ احتياطي للوحة | 2 | يجب التأكد من وجوده |
| QZ Tray | 2 | برنامج على جهاز الكاشير، خارج الخادم |

## 2. قائمة تحقق قبل أول نشر

تُنسخ إلى تذكرة وتُملأ من لوحة المزوّد، لا من الذاكرة.

- [ ] إصدار PHP للويب وللـ CLI مكتوب.
- [ ] الامتدادات في الافتراض A-01 مفعلة.
- [ ] `disable_functions` لا يمنع `proc_open` إن كان Composer على الخادم مطلوباً. النشر المعتمد لا يحتاج `proc_open` في وقت التشغيل إذا رُفع `vendor` جاهزاً.
- [ ] المسار الكامل لثنائي PHP مكتوب، مثال شكلي: `/usr/local/bin/php`.
- [ ] Cron كل دقيقة مسموح.
- [ ] إصدار MySQL/MariaDB و InnoDB و utf8mb4 مكتوبة.
- [ ] يمكن إنشاء مفاتيح أجنبية.
- [ ] موضع جذر الموقع: قابل للتغيير أم `public_html` فقط.
- [ ] `open_basedir` يسمح بقراءة مجلد التطبيق خارج الجذر إن وُضع خارجه.
- [ ] `symlink` مسموح أو سنستخدم مجلد الرفع العام البديل.
- [ ] قيم الذاكرة والرفع والـ `max_input_vars`.
- [ ] SSL مفعل ويجبر HTTPS.
- [ ] حصة القرص والـ Inodes.
- [ ] النسخ الاحتياطي اليومي ومدة الاحتفاظ وطريقة الاسترجاع.
- [ ] اختبار رسالة SMTP وصلت إلى بريد خارجي.
- [ ] ModSecurity لا يرفض أجسام JSON المتوسطة. يُختبر بنموذج طلب فيه 20 بنداً.

إذا فشل CLI أو Cron أو InnoDB أو الذاكرة أقل من 128M تتوقف خطة النشر ويُغيَّر المزوّد. لا نعيد تصميم النظام ليعمل بلا تهجير.

## 3. ترتيب المجلدات

الترتيب المعتمد عندما تسمح الاستضافة بالوصول إلى المجلد الأب (A-06):

```text
/home/{account}/
  restaurant-saas/
    app/
    bootstrap/
    config/
    database/
    resources/
    routes/
    storage/
    vendor/
    .env
    artisan
  public_html/
    index.php          مسارات معدلة تشير إلى ../restaurant-saas
    .htaccess
    build/
    favicon.ico
    robots.txt
```

`index.php` يشير إلى:

```text
../restaurant-saas/vendor/autoload.php
../restaurant-saas/bootstrap/app.php
```

ويُضبط `storage` و `bootstrap/cache` خارج الجذر العام.

`.env` يملك صلاحية قراءة لمستخدم PHP فقط، ولا يُوضع تحت `public_html`.

### 3.1 إذا تعذر المجلد الأب

ترتيب احتياطي، أضعف، يُستخدم فقط بعد إثبات `open_basedir`:

```text
public_html/
  .htaccess              يمنع الوصول إلى كل شيء إلا index.php والأصول
  index.php
  build/
  media/                 رفع عام غير قابل للتنفيذ
  laravel/
    .env
    app/ ... vendor/ storage/
```

قواعد الحجب الدنيا:

```apache
RedirectMatch 403 ^/laravel/
RedirectMatch 403 ^/media/.*\.(php|phtml|phar)$
Options -Indexes
```

على LiteSpeed تُراجع القواعد المكافئة من وثائق المزوّد. هذا الترتيب احتياطي لأن تسريب قاعدة واحدة يفتح الكود. الترتيب الأول هو هدف الإطلاق.

## 4. الصلاحيات

| المسار | الكتابة |
|---|---|
| كل الكود و`vendor` | لا، لمستخدم PHP |
| `storage/` و`bootstrap/cache/` | نعم |
| `public/build` أو `public_html/build` | لا، إلا أثناء رفع الإصدار |
| مجلد الوسائط | نعم للكتابة، لا لتنفيذ PHP |

لا `777`. القيمة العملية على الاستضافة المشتركة غالباً `755` للمجلدات و`644` للملفات، مع مالك هو مستخدم الحساب نفسه فيعمل PHP كمالك. إن فصل المزوّد مستخدم PHP عن مستخدم FTP تُضبط المجموعة حسب تعليماته المكتوبة.

## 5. Composer بلا root

على جهاز التطوير:

```text
composer install --no-dev --optimize-autoloader
```

ثم يُرفع `vendor` مع الإصدار. هذا المسار المعتمد لأن ذاكرة SSH على الاستضافة المشتركة كثيراً ما تقتل Composer.

Composer على الخادم مسار بديل فقط إذا أثبت المزوّد أن CLI والذاكرة يكفيان:

```text
cd /home/{account}/restaurant-saas
/usr/local/bin/php /path/to/composer install --no-dev --optimize-autoloader
```

لا يُشغَّل `composer update` على الإنتاج. القفل يُحدَّث محلياً ويُراجع.

حجم `vendor` يُحسب قبل اختيار الاستضافة حتى لا تُستنزف الـ Inodes. إن كانت الحصة ضيقة تُحذف اختبارات الحزم بعد التثبيت بأداة التنظيف، مع الإبقاء على إمكانية إعادة البناء من القفل.

## 6. التهجير

بعد رفع الإصدار وضبط `.env`:

```text
/usr/local/bin/php /home/{account}/restaurant-saas/artisan migrate --force
```

يُشغَّل من مجلد Cron «أمر لمرة واحدة» أو من SSH للمستخدم إن وُجد. لا تهجير من المتصفح. لا مسار ويب سري يشغل التهجير.

قبل التهجير على إنتاج فيه بيانات: نسخة احتياطية في نفس اليوم، والتهجير يُجرَّب على نسخة القاعدة في حساب الاختبار.

`migrate:fresh` ممنوع على أي قاعدة غير محلية.

## 7. خطوات نشر إصدار

1. بناء الأصول محلياً: `npm run build` على جهاز التطوير.
2. `composer install --no-dev --optimize-autoloader` محلياً.
3. ضغط الإصدار بلا `.env` وبلا `node_modules` وبلا `.git`.
4. رفع الأرشيف إلى مجلد مؤقت خارج الجذر العام.
5. فك الضغط فوق مجلد التطبيق مع الإبقاء على `.env` و`storage` القائمين.
6. تشغيل التهجير.
7. `php artisan config:cache` ثم `route:cache` ثم `view:cache` إذا سمح CLI.
8. مسح OPcache بالطريقة التي يتيحها المزوّد (تبديل إصدار PHP ذهاباً وإياباً غالباً يعمل على cPanel إن لم يوجد زر).
9. فتح صفحة دخول وفحص سجل `storage/logs` لطلب واحد.
10. الإبقاء على الأرشيف السابق 7 أيام للتراجع بفكه، دون تراجع تهجير مدمر. التهجيرات يجب أن تكون أمامية. التراجع عن إصدار يعني كود قديم مع قاعدة جديدة متوافقة، لذلك لا يحذف التهجير عموداً في نفس إصدار الكود الذي ما زال يقرأه.

## 8. الطابور

الإعداد: `QUEUE_CONNECTION=database`.

أمر Cron، كل دقيقة، مهلة 50 ثانية حتى لا يتداخل مع الدقيقة التالية إلا قليلاً:

```text
cd /home/{account}/restaurant-saas && /usr/local/bin/php artisan queue:work database --stop-when-empty --max-time=50 --tries=3 --backoff=30
```

`--stop-when-empty` ضروري حتى لا تبقى عملية بعد انتهاء Cron وتتضاعف العمليات كل دقيقة.

إذا تأخر Cron أو لم يعمل:

| المهمة | الأثر |
|---|---|
| إرسال بريد تأكيد حجز | الحجز محفوظ. البريد يتأخر. الضيف يرى التأكيد على الشاشة. |
| استهلاك وصفة | الرصيد يتأخر. البيع محفوظ. عند عودة العامل تُستهلك مرة واحدة بسبب مفتاح التكرار. |
| ويب هوك دفع | **لا يمر عبر الطابور.** يُعالج في الطلب نفسه لأنه مصدر المال ولأن البوابة تعيد المحاولة. المعالجة قصيرة: تحقق توقيع وتحديث فاتورة. |
| إنشاء تذكرة مطبخ | **داخل معاملة الطلب** لا في الطابور. |
| ملخصات التقارير | تتأخر حتى يعمل المجدول. شاشة اليوم للفرع تحسب الوردية مباشرة. |
| انتهاء الاشتراكات | يتأخر ساعات. الأمر التالي يصحح الحالات من التواريخ. |

المهام التي تدخل الطابور: البريد، ضغط صور إضافي إن لم يكتمل في الطلب، استهلاك المخزون، رسائل لاحقة، إعادة بناء ملخص يوم عند طلب يدوي.

`failed_jobs` تُراجع من شاشة المشرف. لا أفق Horizon.

## 9. المجدول

سطر Cron الوحيد على cPanel:

```text
* * * * * cd /home/{account}/restaurant-saas && /usr/local/bin/php artisan schedule:run >> /home/{account}/logs/schedule.log 2>&1
```

تجربة Windows المحلية ليست Cron. من PowerShell داخل مجلد التطبيق:

```text
php artisan billing:issue-invoices
php artisan billing:advance-states
```

Task Scheduler في Windows يستطيع استدعاء `php artisan schedule:run` كل دقيقة للتجربة فقط. الإنتاج يبقى سطر cPanel، لأن الاستضافة المشتركة لا تشغّل عملية دائمة. تشغيل أمر الفاتورة مرتين يكتب فاتورة واحدة بسبب القيد الفريد `(subscription_id, period_start)`.

المهام داخل التطبيق، كلها `withoutOverlapping` و`onOneServer` غير مستخدم لأنه لا يوجد قفل Redis. `withoutOverlapping` بقفل ملف مقبول على خادم واحد.

| المهمة | التوقيت | الملاحظة |
|---|---|---|
| `billing:advance-states` | كل ساعة | ينقل الحالات حسب التواريخ |
| `billing:issue-invoices` | 02:10 Africa/Cairo | فواتير الفترات القادمة |
| `reports:rollup-daily` | كل ساعة دقيقة 20 | يعيد اليوم وأمس |
| `reservations:mark-no-show-candidates` | كل 30 دقيقة | لا يعلّم تلقائياً إلا بعد مرور المدة وإعداد الفرع. الافتراضي قائمة انتظار للمدير لا وسم صامت. |
| `queue:retry` غير مستخدم عشوائياً | — | الفاشل يُراجع يدوياً |
| تنظيف `sessions` و`idempotency_keys` الأقدم من 14 يوماً | يومياً 03:30 | يمنع تضخم الجداول |

`schedule:run` نفسه يجب أن ينتهي خلال ثوانٍ لأنه فقط يطلق المستحق. العمل الثقيل إما أوامر قصيرة أو دفع Jobs.

سجل Cron يُدار بحجم: سطر التاريخ فقط عند الفشل حتى لا يملأ القرص. التفصيل في `storage/logs/laravel.log` مع تدوير يومي من إعداد Laravel، بحد 14 ملفاً.

## 10. الزمن الحقيقي

| الخيار | التكلفة | الحمل على PHP | الحكم |
|---|---|---|---|
| استطلاع كل 8–15 ثانية | ضمن الاستضافة | طلب خفيف مفهرس يعيد التذاكر المتغيرة بعد `updated_at` | **المعتمد** |
| استطلاع طويل 25 ثانية | ضمن الاستضافة نظرياً | عملية محجوزة لكل شاشة | مرفوض |
| Pusher/Ably | اشتراك شهري + HTTPS صادر | منخفض على PHP | مؤجل حتى يشتكي المطبخ |
| WebSocket على الخادم | VPS أو عملية دائمة | غير متاح | مرفوض للإطلاق |

شاشة المطبخ تطلب فقط تذاكر الحالات المفتوحة للفرع الحالي بعد طابع زمني. الاستجابة بضعة كيلوبايتات. عشر شاشات لفرع تعني حوالي 75 طلباً في الدقيقة لهذا الفرع. هذا مقبول لعدد المنشآت المبكر (عشرات لا آلاف الشاشات). إذا اقترب حد عمليات PHP يُرفع الفاصل إلى 12 ثانية من إعداد النظام `kitchen.poll_seconds` بلا نشر منطق جديد.

لوحة طلبات المدير تستعلم كل 15 ثانية. صفحة الضيف بعد إرسال الطلب تستعلم كل 15 ثانية حتى `ready` ثم تتوقف.

## 11. الكاش

`CACHE_STORE=file`. مناسب لحساب واحد. يُستخدم لكتالوج الميزات الفعّال لمدة 60 ثانية، ولصفحة القائمة العامة لمدة 60 ثانية مع مسح المفتاح عند حفظ منتج في ذلك الفرع.

لا يُخزَّن في الكاش رصيد مخزون ولا إجمالي فاتورة. المال والمخزون يُقرآن من القاعدة.

إذا مجلد الكاش امتلأ أو مُنع، التحويل إلى `database` قرار تشغيل مؤقت مع علم أنه يزيد الاستعلامات. الجدولان `cache` و`cache_locks` يُنشآن في التهجير حتى يكون التحويل تغييراً في `.env` فقط.

## 12. الجلسات

`SESSION_DRIVER=database`. عمر الجلسة 8 ساعات للموظف و12 ساعة للكاشير إذا بقيت الوردية، مع تجديد النشاط. ضيف القائمة بلا جلسة إلزامية؛ رمز CSRF لصفحة الطلب يكفي.

`SESSION_SECURE_COOKIE=true` و`SameSite=lax` في الإنتاج.

## 13. الصور

| الأصل | الحد قبل الضغط | الناتج |
|---|---|---|
| شعار | 2 ميغابايت | 512 بكسل PNG أو WebP |
| غلاف القائمة | 4 ميغابايت | عرض 1600 |
| صورة منتج | 4 ميغابايت | عرض 1600 وجودة 82 |
| QR | يُولَّد على الخادم | PNG صغير |

الرفض إن فشل فحص الصورة أو كان المقاس صفراً. لا رفع SVG في الإطلاق لأن SVG قد يحمل سكربت.

عند اقتراب حصة القرص من 80٪ تُنقل الوسائط الجديدة إلى تخزين متوافق مع S3 (قرار تشغيلي لاحق). الروابط تُحفظ كمسار نسبي أو كمفتاح كائن، لا كرابط نطاق ثابت داخل صفوف الطلبات. الطلبات لا تعتمد على صورة المنتج بعد التثبيت؛ الصورة للعرض الحي فقط.

## 14. البريد وواتساب

البريد: `MAIL_MAILER=smtp` بمضيف ومنفذ 587 وTLS. الرسائل:

- دعوة موظف وإعادة كلمة المرور.
- تأكيد حجز.
- تذكير اشتراك.
- إشعار تذكرة دعم.

القالب نص عربي وإنجليزي حسب لغة المستخدم. لا مرفقات كبيرة.

واتساب: زر في شاشة الحجز والطلب يفتح

```text
https://wa.me/{phone}?text={encoded}
```

الرقم رقم المنشأة الذي أدخله المالك. لا رمز API. الإرسال الآلي لاحقاً عبر مزوّد رسمي بحقول `provider` و`provider_ref` في `outbound_messages` حتى لا يُعاد تصميم الجدول.

## 15. اعتمادية نقطة البيع

نقطة البيع صفحة ويب على Chrome أو Edge حديث على تابلت أو حاسوب. لا تطبيق متجر.

| الموضوع | سلوك الإصدار الأول |
|---|---|
| الطباعة | تنسيق 80 مم ثم حوار طباعة المتصفح. الطابعة الحرارية تُعرَّف على الجهاز كطابعة نظام. |
| انقطاع قبل الاستجابة | الواجهة تحتفظ بالسلة في الذاكرة وتعرض «لم يُؤكد». لا تعتبر البيع ناجحاً بلا رقم فاتورة من الخادم. |
| انقطاع بعد نجاح الخادم وفقدان الاستجابة | إعادة المحاولة بنفس `idempotency_key` تُرجع نفس الفاتورة. |
| الضغط المزدوج | الزر يُعطل حتى تنتهي الرحلة، والمفتاح يحمي الخادم. |
| أوفلاين كامل | غير متاح. لا إنشاء فواتير محلية. |
| وردية مفتوحة وانقطع النت | الوردية تبقى مفتوحة على الخادم. الكاشير يكمل عندما تعود الشبكة. النقد الذي استلمه بيده خارج النظام يُسجل لاحقاً بحركة إدخال بصلاحية مدير، لا بفاتورة وهمية. |
| تعدد الكاشيرين | كل واحد ورديته. الصندوق الواحد وردية مفتوحة واحدة. |

مفتاح منع التكرار: ULID ينشئه المتصفح عند فتح شاشة التحصيل ويبقى ثابتاً حتى النجاح أو إلغاء السلة.

ما هو واقعي في الإصدار الأول: تحمل إعادة الإرسال، ومنع التكرار، ورسالة انقطاع واضحة، وطباعة بعد عودة النجاح. غير الواقعي: بيع واستمرار وردية وأسعار محدثة بلا شبكة.

## 16. الأسرار

`.env` يحتوي اتصال القاعدة والبريد ومفاتيح البوابة. لا يُرفع للمستودع. على جهاز التطوير ملف `.env` محلي فقط عندما يبدأ التنفيذ لاحقاً. الإنتاج يُكتب من مدير الملفات أو محرر اللوحة.

تدوير مفتاح التطبيق `APP_KEY` يُبطل الجلسات. لا يُغيّر إلا بخطة.

## 17. التراجع

1. إبقاء أرشيف الإصدار السابق.
2. إذا فشل التهجير تتوقف الخطوات وتُستعاد النسخة الاحتياطية لقاعدة البيانات قبل إعادة المحاولة على الاختبار.
3. لا نشر مساء الجمعة لأول إصدار إنتاجي. أول نشر في يوم يمكن فيه مراقبة السجلات ساعتين.

## 18. المراقبة الممكنة بلا خدمات إضافية

- فحص يدوي يومي لأول أسبوعين لـ `failed_jobs` وحجم `storage/logs` ومساحة القرص من cPanel.
- صفحة `/health` تعيد 200 ونصاً بسيطاً بلا أسرار إذا اتصلت القاعدة. لا تفاصيل إصدار للعموم بعد الإطلاق؛ تُقيَّد بعنوان IP للمشرف أو تُغلق وتُستبدل بفحص من Cron يكتب في السجل.
- تنبيه البريد للمشرف عند فشل أمر الفوترة. إذا كان البريد نفسه تالفاً، السجل في cPanel هو المرجع.

لا New Relic ولا عميل يحتاج root في الإطلاق.
