# 18 — أرشيف الإصدار وخطة التراجع (P7-S18-05)

## أين يُحفظ الأرشيف

خارج الجذر العام دائماً، مثال cPanel:

```text
/home/{account}/releases/
  restivo-YYYYMMDD-HHMM.tar.gz          ← الإصدار الحالي قبل النشر التالي
  restivo-YYYYMMDD-HHMM.tar.gz          ← السابق (يُبقى ≥ 7 أيام)
```

لا تُوضع الأرشيفات تحت `public_html` ولا تحت `public/`.

محتوى الأرشيف: كود التطبيق بلا `.env` وبلا `node_modules` وبلا `.git`، مع `vendor` و`public/build` إن كان النشر يعتمد الرفع المحلي.

## قبل كل نشر

1. أخذ أرشيف المجلد الحالي → `/home/{account}/releases/`.
2. أخذ نسخة قاعدة (JetBackup / mysqldump) بنفس الختم الزمني إن أمكن.
3. التأكد أن التهجيرات أمامية فقط (لا حذف عمود ما زال الإصدار السابق يقرأه).

## التراجع

1. وضع صيانة قصير إن لزم (`maintenance.enabled` أو صفحة المزوّد).
2. فك أرشيف الإصدار السابق فوق مجلد التطبيق مع الإبقاء على `.env` و`storage`.
3. **لا** تشغيل تهجير عكسي مدمر. إن كان التهجير الجديد متوافقاً أمامياً يبقى؛ وإلا تُستعاد قاعدة النسخة الاحتياطية المأخوذة قبل النشر.
4. `php artisan config:cache` (وما يتاح من route/view cache).
5. فتح صفحة الدخول + بيع تجريبي واحد + مراجعة `ops:health-check`.
6. إبقاء الأرشيف الفاشل 7 أيام للتحليل ثم حذفه يدوياً.

## ما لا يُفعل

- لا نشر مساء الجمعة لأول إنتاج.
- لا حذف عمود في نفس الإصدار الذي ما زال الكود الحي يقرأه.
- لا الاعتماد على Git داخل الاستضافة المشتركة للتراجع — الأرشيف هو المرجع.
